# おでかけナビ なかつ

スマホの操作に慣れていない中津市の高齢者を想定した、バス乗り換え案内アプリの体験版です。企画書の「自宅を登録する → 目的地・到着時刻を選ぶ → お迎えの申込内容を確認する → 乗り換え案内を見る」という流れを試せます。

**実際の運行情報・予約システムとは連携していません。** 施設名は中津市内の施設を参考にしていますが、時刻・運賃・バスの経路・バス停はサンプルです。国土地理院の航空写真と端末の現在地は実際の位置の確認に使えますが、表示するバス経路は実際の運行案内ではありません。予定を保存しても交通事業者へ予約は送信されません。

## 開発を始める

Node.js 24・npm 11 で動作確認しています。既存の `/workspace/-navi-` チェックアウトを利用します。

接続情報が未設定でも、端末内に保存するゲスト体験版として起動できます。メール登録・ログインと本人用データの保存には **Supabase プロジェクト・RLS の SQL 適用・メール配信・公開用接続情報**の設定が必要です。[認証の接続手順](docs/auth-setup.md)を参照してください。未設定時は「ログインの準備中」と表示し、仮のログインを成功させることはありません。

```bash
cd /workspace/-navi-
npm ci --cache /tmp/navi-npm-cache
npm run dev
```

開発サーバーは `0.0.0.0` のポート `5173` で起動します。ポート使用中の場合は自動で別ポートへ切り替わらず終了するため、既存のサーバーを確認してください。クラウド環境では上記のキャッシュ指定を使うと、ホームディレクトリへの書き込み権限に依存せず導入できます。

## 確認コマンド

```bash
npm run build
npm test
npm run test:e2e
npm run test:auth
npm run test:production
```

- `build`：TypeScript の型検査と本番用ビルド。生成先は `dist/`。
- `test`：経路計算・入力検証・ブラウザ保存処理の単体テスト。
- `test:e2e`：Chromium でデスクトップとスマートフォンの操作を確認。自宅登録、経路検索、申込体験、再読み込み後の復元、案内、削除、航空写真・現在地の許可と停止などを検証。位置情報はブラウザのテスト機能で再現します。
- `test:auth`：実際の認証 SDK とテスト用 HTTP 応答で、登録・ログイン・データの分離などを確認。実プロジェクトや実メールを使用するテストではありません。
- `test:production`：公開用ビルドを作成し、ドメイン直下と `/-navi-/` 配下の両方でファイルの読み込み・自宅登録・経路検索を確認。GitHub Pages の公開前にも実行します。

E2E は利用可能なら `/usr/bin/chromium` を、なければ Playwright でインストールした Chromium を使用します。`PLAYWRIGHT_CHROMIUM_EXECUTABLE` で実行ファイルを指定することもできます。他の環境では `npx playwright install --with-deps chromium` でブラウザを用意してください。ゲスト画面のテストは接続設定を明示的に空にした専用サーバー（ポート `5174`）、認証テストはHTTP応答を再現する専用サーバー（ポート `5175`）を起動します。実際の開発サーバーや Supabase プロジェクトは再利用しません。テスト時は該当ポートを空けてください。失敗時の画面・トレースは `test-results/` に出力します。

## GitHub Pages で公開する

公開先は [おでかけナビ なかつ](https://5rych9-star.github.io/-navi-/) です。

初回のみ、リポジトリの **Settings → Pages → Build and deployment → Source** を **GitHub Actions** に設定してください。「Deploy from a branch」でソースの `index.html` をそのまま配信すると、ブラウザでは TypeScript を実行できず、白紙になる場合があります。

`.github/workflows/deploy-pages.yml` は `main` へのプッシュ時に、次の処理を実行します。

1. Node.js 24 で `npm ci` により依存関係を導入する。
2. `npm test` と `npm run test:auth` で、単体テストとテスト用HTTP応答によるログイン・本人データの分離を確認する。
3. `npm run test:production` で `dist/` を生成し、ルートと `/-navi-/` の両方で表示・検索できることをブラウザで確認する。
4. `dist/` だけを GitHub Pages にデプロイする。

GitHub に標準で用意されるワークフロー用トークンを使用するため、API キーや個人用トークンの追加は不要です。このワークフローが Pages の Source 設定を自動変更するわけではありません。

ログインを公開先で有効にする場合は、Repository variables に `VITE_SUPABASE_URL` と `VITE_SUPABASE_PUBLISHABLE_KEY` を設定して再ビルドします。値はブラウザへ公開されるため、Supabase の管理者用キーや SMTP パスワードを設定しないでください。Supabase の設定と一般利用者へのメール配信については[認証の接続手順](docs/auth-setup.md)にまとめています。

Source の変更前にワークフローが失敗していた場合は、リポジトリの **Actions → Deploy to GitHub Pages → Run workflow** で `main` を選び、再実行してください。`build` と `deploy` の両方が成功したら公開先を再読み込みします。以前の白紙画面が残る場合は、ブラウザを強制再読み込みしてください。

ビルドでは相対パスを使用するため、`/-navi-/` のようなサブディレクトリ配信と、Vercel などのドメイン直下の配信に対応します。ローカルの Vite 開発サーバーも同じコードで利用できます。

## 試せる機能

- Supabase 設定後は、メール・パスワードでの新規登録、確認メール、ログイン・ログアウト、パスワード再設定、自分のアカウントへの自宅・予定保存。
- ニックネームと自宅の地域・地図上の位置を登録。必要なときだけ国土地理院の航空写真を開き、実際の場所を確認できます。
- 「耶馬溪周辺を見る」で地域へ移動し、「写真を詳しく見る」で元画像の詳細を表示。「地図を大きく表示」で表示範囲を広げられます。これらの表示操作では自宅登録を変更しません。
- 端末の現在地を地図に表示。位置取得は利用者の操作とブラウザの許可が必要で、停止できます。現在地を自宅として使う場合は、明示的に選択して登録します。
- 目的地・日付・到着希望時刻から、デマンドバスと路線バスを組み合わせたサンプル経路を検索。バス停まで歩く候補も表示。
- お迎え内容を確認し、実際の予約が送信されないことに同意して体験用の予定を保存。
- 保存した予定から徒歩・お迎え・路線バスの案内を順番に確認。対応ブラウザでは音声読み上げも利用可能。
- 文字サイズ切り替え、スマートフォン用メニュー、使い方と登録情報の削除。

## 保存する情報

保存先は接続設定によって変わります。

| 利用状態                      | 自宅・ニックネーム・予定の保存先                                |
| ----------------------------- | --------------------------------------------------------------- |
| Supabase 未設定のゲスト体験版 | 同じブラウザの `localStorage`                                   |
| Supabase 設定後、ログイン済み | Supabase の本人用データ。RLS で他アカウントからの読み書きを拒否 |
| Supabase 設定後、未ログイン   | 自宅・予定の保存にはログインが必要                              |

ゲスト体験版で使用するキーは次のとおりです。旧ゲストデータを、ログインしたアカウントへ自動アップロードすることはありません。

| キー                 | 内容                                   |
| -------------------- | -------------------------------------- |
| `nakatsu-profile-v1` | ニックネーム・自宅                     |
| `nakatsu-trips-v1`   | 予定・選択した経路・その時点の登録情報 |

ゲストデータは別の端末やブラウザとは共有されず、ブラウザの保存データを消すと復元できません。接続済みアカウントでは、同じアカウントでログインしてサーバー上の保存データを読み込みます。認証セッションはタブ単位の `sessionStorage` に保持し、再読み込み時に復元します。パスワードそのものはブラウザの保存領域に保管しません。

「使い方」→「登録情報を削除する」から、本人の自宅・予定を削除できます。ログイン用アカウント自体は残ります。ゲスト体験版ではこのブラウザ内のデータを削除します。個別の予定は「おでかけ予定」から削除できます。

Web ページ自体は公開ですが、別利用者へ本人の自宅・予定を共有する機能はありません。アカウントの情報はサーバー側の RLS でも制限します。共有端末では利用後にログアウトし、以前のゲスト体験データがある場合は端末内の登録情報も削除してください。

現在地は取得中のメモリ上で扱い、移動履歴として保存・アップロードしません。取得は停止操作、地図や画面を閉じたとき、タブが非表示になったときに停止します。「現在地を自宅に設定」で選び、登録を確定した場合は、その位置がゲストの自宅座標、またはアカウントの自宅情報として保存されます。保存済み予定にも、保存時点の自宅情報が含まれます。

サンプルの経路計算は端末内で行います。ログイン・アカウントへの保存・航空写真の表示にはインターネット接続が必要です。オフラインでの再読み込みには対応していません。

## 航空写真と現在地

地図には Leaflet 1.9.4 を使用し、国土地理院の「全国最新写真（シームレス）」を表示します。API キーは不要です。

- タイル：`https://maps.gsi.go.jp/xyz/seamlessphoto/{z}/{x}/{y}.jpg`
- 取得画像のズーム：2〜18。画面では20まで拡大できますが、18より先は元画像の拡大で、写真の解像度が上がるわけではありません。
- 出典：[地理院タイル](https://maps.gsi.go.jp/development/ichiran.html)
- 利用条件：[国土地理院コンテンツ利用規約](https://www.gsi.go.jp/kikakuchousei/kikakuchousei40182.html)
- 写真の説明・承認情報：[詳細解説](https://cyberjapandata.gsi.go.jp/legend/seamlessphoto.pdf)／[承認番号](https://cyberjapandata.gsi.go.jp/legend/seamlessphoto_precaution.pdf)

航空写真の読み込みと現在地の取得は、どちらも最初は停止しています。航空写真を有効にすると、国土地理院へ IP アドレスと表示範囲に対応する画像のリクエストが送られます。自宅マーカーやニックネームそのものを送る処理はありませんが、閲覧範囲は画像リクエストから分かるため、外部への位置に関する通信が一切ないわけではありません。画面の説明を確認してから有効にしてください。

写真は撮影済みの画像で、リアルタイム映像ではありません。地域ごとに撮影時期・解像度が異なり、第三者由来の写真も含まれます。地図上の出典表示と公式利用条件を維持してください。

高密度画面では、対応する画像を高密度表示しつつ、取得するタイルのズームが18を超えないようにしています。耶馬溪も含め、元画像そのものにない細部を作り出す機能ではありません。

現在地の取得には HTTPS（ローカル開発では localhost）とブラウザの位置情報許可が必要です。位置情報が拒否・未対応・取得失敗の場合は、地域選択や地図での手動設定を利用できます。端末や受信環境による誤差があるため、表示位置を確認してから自宅に登録してください。

クラウド検証環境では国土地理院への通信が制限される場合があります。ブラウザテストでの許可・停止・エラー処理の確認と、実端末での航空写真・位置精度の確認は別に行ってください。

## 実運用へ進めるために

現在の実装は操作検証用です。実運用には、次の仕様・連携を交通事業者などと確認し、実装・検証する必要があります。

1. 公式時刻表・GTFS などの利用許諾と更新方法、運行日・運休・乗り継ぎを考慮した経路検索。
2. デマンド交通の対象地域・利用資格・事前登録・予約期限・定員・料金などの運行条件。
3. 事業者の予約 API または実際の受付手段との連携と、受付・確定・取消の状態管理。端末内の予定保存と予約確定の区別。
4. 航空写真・端末位置情報の精度の実地確認、住所検索・安全な徒歩経路の提供元と利用条件。
5. Supabase・メール配信の実接続、RLS の実 DB テスト、個人情報の運用・削除方針、事業者との連携確認。

認証 SDK の応答を再現するブラウザテストと、実際の確認メール・Supabase データベースの検証は別です。SQL の権限テストは `supabase/tests/private_travel_data.sql` にあります。ローカル PostgreSQL 17 では本人・他人・匿名のアクセス制限を確認済みですが、実際に利用する Supabase プロジェクトでも適用・実行する必要があります。実データへの置き換え後は、高齢の利用者による操作確認と実際の運行条件での検証も必要です。

ローカルで PostgreSQL のサーバー・クライアントが利用できる場合は、`bash scripts/test-rls-local.sh` で一時的なソケット専用 DB を作って権限 SQL を検証できます。既存の DB や Supabase には接続せず、終了時に一時 DB を削除します。必要に応じて `NAVI_PG_BIN` でバイナリのディレクトリを指定してください。
