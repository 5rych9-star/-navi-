# メール登録・ログインの接続設定

このアプリは Supabase Auth でメール登録・ログインを行います。自宅・ニックネーム・予定は、ログイン後も同じ端末のブラウザ内に保存します。自宅の座標が予定内の登録情報・経路 ID・地名にも含まれるため、予定全体もサーバーには送信しません。Supabase Database は旧版で保存したデータを端末へ移し、削除するためだけに使用します。プロジェクト未設定の状態では端末内のゲスト体験版になり、ログイン画面に「準備中」と表示します。

実際のプロジェクトへの接続、メール配信、データベースへの SQL 適用は、以下の設定が必要です。画面や HTTP 応答を再現したテストの成功は、実メールの到着や実データベースでの権限検証を完了したことにはなりません。

## 1. Supabase プロジェクトを作る

[Supabase](https://supabase.com/) にログインし、新しいプロジェクトを作成します。プロジェクトの URL と **Publishable key** を設定画面から確認します。公開用キーを使い、`service_role` や `sb_secret_` で始まる管理者用キーは使いません。

DB 管理パスワードやメール送信サービスのパスワードを、チャット・ソースコード・GitHub の公開変数に入力しないでください。

## 2. 旧版の保存を停止し、移行用のアクセス制限を作る

同じプロジェクトの **SQL Editor** で、未適用のファイルを番号順に一度ずつ実行します。

1. [`202610270001_private_travel_data.sql`](../supabase/migrations/202610270001_private_travel_data.sql)：旧データの移行元テーブルと本人用のアクセス制限を作成。
2. [`202610280001_device_only_travel_data.sql`](../supabase/migrations/202610280001_device_only_travel_data.sql)：追加・更新の権限とポリシーを撤回し、本人の読み取り・削除だけを許可。

既に初回 SQL を適用済みなら、2番目だけ実行します。新規プロジェクトでも両方を順に適用し、アプリに接続情報を設定する前に2番目まで完了してください。初回の作成 SQL を重ねて実行すると重複エラーになります。

新版アプリは自宅・予定を追加・更新する HTTP リクエストを送りません。さらに2番目の SQL を適用すると、開いたままの旧版アプリから送られた保存要求もデータベースで拒否します。RLS は引き続き有効で、移行元テーブルは本人の行だけ読み取り・削除できます。**Table Editor** で INSERT・UPDATE ポリシーがなく、SELECT・DELETE ポリシーだけ残っていることを確認してください。

このリポジトリの変更や GitHub Pages の再公開だけでは、利用中の Supabase に SQL は適用されません。**ホスト側の SQL 適用と既存データの削除状況は、実際のプロジェクトで確認が必要です。**

### 旧版でサーバーに保存したデータ

新版にログインすると、本人の旧データを取得し、このブラウザへの保存に成功してからサーバーの行を削除します。端末側に既存データがあれば、端末の自宅情報を優先し、予定は同じ ID の端末版を優先して統合します。保存に失敗した場合はサーバーの行を削除しません。削除に失敗した場合は、削除未確認の案内を表示しつつ端末内のデータを利用・保存でき、再読み込みで移行を再試行します。移行済みとして記録された後は、旅行データの読み取り・削除リクエストも送りません。ログインしていない利用者の旧データは、この処理だけでは削除されません。データを失わないよう、マイグレーション自体には全件削除を含めていません。

サーバーから直ちにすべての旧自宅・予定を削除する運用では、**未移行のデータを復元できなくなることを確認したうえで**、プロジェクト管理者が SQL Editor で次を実行します。ログインアカウントは削除しません。

```sql
-- 未移行分も含め、すべての旧自宅・予定を削除する操作です。
begin;
delete from public.user_travel_data;
select count(*) as remaining_legacy_records from public.user_travel_data;
commit;
```

削除後の行数が0であることを確認します。過去のバックアップ・ログ等の保持は別管理なので、Supabase の保持期間・削除手続きもプロジェクトの運用設定で確認してください。管理者用キーや DB パスワードをアプリに設定する必要はありません。

## 3. メール登録と確認リンクを設定する

**Authentication** で次を設定します。

- Email プロバイダーと新規ユーザー登録を有効にする。
- メール確認を有効にする。
- パスワードの最小文字数を8文字以上にする。アプリの新規登録・再設定は8〜128文字に対応します。

**Authentication → URL Configuration** の値を、末尾の `/` を含めて設定します。

| 項目          | 値                                      |
| ------------- | --------------------------------------- |
| Site URL      | `https://5rych9-star.github.io/-navi-/` |
| Redirect URLs | `https://5rych9-star.github.io/-navi-/` |

ローカル開発でも確認メールやパスワード再設定を試す場合だけ、使う開発元と一致する `http://127.0.0.1:5173/` または `http://localhost:5173/` を Redirect URLs に追加します。Vercel や独自ドメインへ変更した場合は、その公開先も正しく設定してください。アプリは、開いているサイトのオリジンとアプリのパスから戻り先を作ります。

確認・再設定メールには Supabase の有効な確認リンクを使用します。独自のメールテンプレートを変更する場合は、[公式の Redirect URLs の説明](https://supabase.com/docs/guides/auth/redirect-urls)も確認してください。

## 4. 一般利用者向けのメール配信を設定する

**任意のメールアドレスで登録を受け付けるには、カスタム SMTP の設定が必要です。** Supabase の標準メール送信は試用向けで、プロジェクトの組織チームに登録されたメールアドレス以外への配信は制限されています。

メール送信サービスを用意し、Supabase の **Authentication → SMTP Settings** でホスト・ポート・ユーザー・パスワード・差出人を設定します。送信元ドメイン等の確認は、選んだサービスの案内に従ってください。SMTP のパスワードは Supabase 側だけに設定し、`VITE_` 変数には入れません。

公式資料：[Send emails with custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp)

## 5. アプリへ公開用の接続情報を設定する

必要な値は次の2つです。

| 変数                            | Supabase から取得する値                          |
| ------------------------------- | ------------------------------------------------ |
| `VITE_SUPABASE_URL`             | HTTPS の Project URL。API のパスやキーを付けない |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Publishable key。管理者用キーは不可              |

これらの `VITE_` 値はビルド済み JavaScript に含まれ、ブラウザから読めます。Publishable key は公開を前提としたキーで、旧版の移行元レコードを保護するのは手順2の RLS と各ユーザーのログイン状態です。新しい自宅・予定の保存先はブラウザ内です。管理者用キーは権限制限を迂回できるため、公開設定には使用できません。

### ローカル開発

リポジトリ直下に `.env.local` を作り、`.env.example` の2項目へ自分のプロジェクトの値を設定してから、開発サーバーを再起動します。既存の `.env.local` がある場合は上書きせず、該当項目を編集してください。`.env.local` は Git の管理対象外です。

### GitHub Pages

リポジトリの **Settings → Secrets and variables → Actions → Variables** で、上記2つを Repository variables として追加します。ワークフローはこの公開値をビルド時に読み込みます。

管理者用キーや不完全な接続値が指定された場合は、公開 JavaScript に出力する前にビルドを失敗させます。値を修正してから再実行してください。

設定後は **Actions → Deploy to GitHub Pages → Run workflow** で `main` を再実行します。環境変数はビルド時に埋め込まれるため、公開ページの再読み込みだけでは設定が反映されません。Pages の Source は **GitHub Actions** にしてください。

## 6. 実接続で確認する

1. 組織チーム以外の、自分で受信できるメールアドレスで新規登録し、確認メールを開く。
2. そのアカウントでログインし、自宅と体験用の予定を登録する。同じブラウザで再読み込み後も復元でき、保存操作で `user_travel_data` への POST・PATCH が発生しないことを Network パネルで確認する。
3. ログアウトし、自宅・予定・現在地が画面に残らないことを確認する。
4. 別アカウントでログインし、最初の利用者の自宅・予定が見えないことを確認する。
5. 旧版のサーバーデータがある場合は、端末に保存されたこととサーバーの本人行が削除されたことを確認する。別端末には自宅・予定が自動同期されないことも確認する。
6. パスワード再設定メールから新しいパスワードを設定し、再ログインできることを確認する。

権限 SQL は、ローカル PostgreSQL 17 の一時 DB で本人の旧データの読み取り・削除、他人・匿名ユーザーの拒否、旧版からの追加・更新・upsert の拒否を実行して確認済みです。実際の Supabase Auth・メール配信・公開プロジェクトの疎通確認は別途必要です。

現在の権限回帰テストは [`supabase/tests/device_only_travel_data.sql`](../supabase/tests/device_only_travel_data.sql) にあります。**検証用プロジェクト**へ両方のマイグレーションを適用した後、SQL Editor 等の管理者接続で実行してください。2利用者と匿名ユーザーで確認し、最後にテストデータをロールバックします。アプリの JavaScript テストだけでは、この SQL は実行されません。`private_travel_data.sql` は初回マイグレーションだけを適用した状態の旧仕様テストで、2番目の適用後には使用しません。ローカル検証スクリプトはこの順序も確認します。

## 保存・削除とログイン状態

- 自宅・ニックネーム・予定は、ゲストでもログイン後でもブラウザの `localStorage` に保存します。ログイン後はアカウントごとに分け、別アカウントのデータを画面へ読み込みません。別端末・別ブラウザへの同期は行わず、ブラウザの保存データを消すと復元できません。
- 端末内の保存は暗号化保管ではありません。同じ端末のブラウザ保存領域を調べられる人からの保護は、端末のロックや利用者別のブラウザプロフィールで行ってください。共有端末から自宅・予定自体を消す場合は、ログアウト前に「登録情報を削除する」を使用します。
- アカウント用の端末保存キーは `nakatsu-account-travel-v2:${userId}` です。端末内の旧ゲストデータを、自動でアカウントへ取り込んだりアップロードしたりすることはありません。
- 認証セッションはタブ単位の `sessionStorage` に保持し、再読み込み時に復元します。アプリは認証 SDK のタブ間通知も分離しています。パスワードそのものはブラウザの保存領域に保管しません。共有端末では利用後にログアウトしてください。
- 「登録情報を削除する」は、本人の自宅・予定を削除します。ログイン用アカウント自体は残ります。
- GPS の現在地は履歴としてアップロードしません。「現在地を自宅に設定」して登録を確定した場合だけ、その位置を端末内の自宅情報として保存します。
- 航空写真の取得先には、IP アドレスと閲覧範囲に対応するリクエストが届きます。ログイン機能の有無で、この通信先がなくなるわけではありません。

Web サイト自体は公開です。一般公開される画面・ソースコードと、利用者ごとに制限する自宅・予定データは分けて扱います。
